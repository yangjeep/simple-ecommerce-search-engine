# athos80-eval — bounded, isolated behavior experiment

**Imported from source revision v1.1.1, with runtime contract v1.1.**
This repository integration uses unmodified main `commerce-core`; it does not
include the earlier inactive PLP-ablation additions. Historical measured binary
hashes are evidence identifiers, not checksums promised for a new build.
See [the experiment report](../../docs/experiments/ATHOS80_FIRST_ITERATION.md).

**Not Athos compatibility; not “80% achieved”; not “20% cost achieved”.** This
crate independently implements a public-behavior-inspired experimental contract.
It has no proprietary implementation dependency, online model call, production
catalog, remote write, or change to the frozen `/plp` service. `src/schema.rs` is
the complete strongly typed JSON schema; unknown input fields are rejected.
Readable draft-2020-12 schemas are in [`schema/`](schema/), generated by
`scripts/athos80_json_schema.py` and checked against all included JSON fixtures.
The existing `commerce-core` is reused for typed same-variant constraints and
immutable indexes. All new serving logic lives in this experimental crate.

## Run

From the repository root (Rust 1.90, pinned workspace Cargo.lock):

```bash
cargo test -p athos80-eval --all-features
cargo clippy -p athos80-eval --all-targets --all-features --no-deps -- -D warnings
cargo fmt -p athos80-eval -- --check
# Actual fixture path:
cargo run -p athos80-eval --bin athos80_replay -- crates/athos80-eval/examples/replay.json
cargo run -p athos80-eval --features bm25 --bin athos80_server -- \
  crates/athos80-eval/examples/catalog.json --addr 127.0.0.1:18780 --workers 1 --bm25 --trace
curl -sS -H 'Content-Type: application/json' \
  --data-binary @crates/athos80-eval/examples/request-bm25-literal.json http://127.0.0.1:18780/search
```

`--bm25` builds an additional index; the binary must have the `bm25` feature.
`POST /search` accepts one Request. `GET /health` reports build capabilities.
`POST /debug/lexical` is available **only with `--trace`** and returns every
pre-filter lexical candidate and score for independent public/synthetic replay.
The harness binds loopback only, uses a fixed 1–64 worker count (default 1),
closes each HTTP/1.1 connection, rejects chunked encoding/duplicate Content-Length,
and limits headers/body to 16 KiB/8 MiB with an absolute 5-second header/body read deadline (not reset per packet).
The POSIX accept backlog is explicitly 128; fixed workers accept directly with
no unbounded user-space connection queue. HTTP rejects (never truncates) q>4096
bytes, >64 filters/rules/signals/context-tags, >16 facets, page limit>1000, >16
conditions/rule, >4096 IDs/target, or >32 filters/target. Offline replay remains
uncapped for trusted frozen experiments. Work remains proportional to the
operator-loaded catalog; this is not an execution-time isolation guarantee. It is not
production HTTP: no TLS/auth/persistence/tenant routing/rate limiting/HA/updates.
This HTTP worker/connection design must be held constant in cost comparisons.

## Four named lexical profiles (v1.1)

* `{"profile":"exact_token_and"}` (default): lowercase Unicode alphanumeric
  exact token AND across title and effective same-variant `Text` attributes;
  empty-token query browses all. Does not index Enum values, stem, typo-correct,
  or calculate BM25. Every candidate has score 1 and relevance bucket 0.
* `{"profile":"supplied","hits":[...]}`: frozen complete lexical universe,
  with `(product_id,variant_id,score,relevance_bucket)`. Caller is responsible
  for completeness; the engine cannot prove recall. IDs must exist and pair,
  hits must be unique, scores finite in [0,1e12]. All hard constraints are
  reverified. This seam lets a mature delegate supply approved relevance tiers.
* `{"profile":"bm25_literal"}` (**new in v1.1**, storefront free text):
  uses the **same installed index analyzer** as both indexed fields: Tantivy
  default `SimpleTokenizer → RemoveLongFilter(limit=40 UTF-8 bytes) → LowerCaser`.
  No stemming/stopword filter is installed; words such as `AND`, `OR`, `the`
  remain ordinary required tokens. Normalized repeated tokens are deduplicated
  preserving first occurrence, so repetition does not silently multiply scores.
  Build an AND (`MUST`) of unique tokens, with each token an OR (`SHOULD`) across
  title and effective same-variant text. Quotes, colons, carets and parentheses
  are **not query DSL**. No QueryParser, query rewriting, selective fallback or
  per-query profile switching is used. Blank/whitespace q browses; a nonblank
  q yielding no analyzed tokens (punctuation-only or only removed long tokens)
  returns zero hits, never implicit browse. Tokens of 40+ UTF-8 bytes are removed
  by the same analyzer at indexing and query time. It uses the same variant
  index, complete-candidate collector, score validation, bucket-0 policy and
  trace seam as strict BM25. This is literal token search, not phrase/synonym/
  typo/product-intent equivalence.
* `{"profile":"bm25"}` (optional feature/index): **Tantivy 0.22.1 variant-doc
  profile**, one document per variant, fields `title` and `text` (effective
  same-variant Text attributes), default Tantivy `TEXT` analyzer, strict
  QueryParser, AND default. Explicit query syntax such as OR/phrases is parsed
  by Tantivy; malformed syntax is an error, never silently an empty result.
  Blank query is AllQuery. Retrieve all matching variant documents before
  hard filters, facets, ranking/grouping and pagination; IDs remain u64.
  All relevance buckets are explicitly **0**, raw BM25 scores retained.
  Computed scores outside finite [0,1e12] fail explicitly, matching the supplied
  replay domain; signed score zero is canonicalized to +0.
  Thus merch can outrank any raw BM25 score within this single bucket. This
  is not Athos tier parity or product-intent relevance. Variant-based document
  frequencies differ from the older product-document delegate: no previous
  NDCG result transfers. Index build/RAM/CPU cost must be counted separately.

No profile changes automatically or falls back silently. Optional BM25 request
without its index/feature fails explicitly. Lexical scope is retained during
self-excluding facets; filtering lexical retrieval prematurely would be wrong.

## v1.1 experimental request/result contract

Defaults are **design assumptions, not user-confirmed Athos behavior**:
`result_mode=products`, `facet_count_mode=null` (follow result mode),
`in_stock_only=true`, `sort=relevance`, `sort_policy=shopper_overrides`,
`offset=0`, `limit=20`, no rules/factors. All are echoed or explained in output.

1. Candidate eligibility is conjunction of typed hard filters over **one exact
   variant**, lexical membership, stock policy and all active hides. Stock
   requires status `in_stock=true` **and** `available_units>0`. No rule, factor,
   pin, or sibling can create eligibility. Unknown rule/factor target IDs are
   unmatched no-ops; unknown supplied lexical IDs are errors.
2. Rank **every eligible variant**, never an early top-N sample. Comparator:
   relevance bucket descending → ordered merchant tuple descending (axis
   order ascending) → `(lexical_score × bounded personal_factor)` descending
   → requested price subsort → product ID then variant ID ascending.
   Exact price is integer USD cents; missing/negative prices unsupported.
   Score composition preserves lexical signal; no `execute_ranked` branch.
3. Merchant group rules use whole-set scope override: query > category > global.
   The highest triggered scope wins even if its target matches no candidate.
   Query matching normalizes with exact tokenizer; category scope reads ONLY
   `context.category_id`, not an inferred category from filters. Conditions
   are AND. Within one axis, matching rule conflict wins higher priority then
   lexicographically smaller ID. Unmatched axis=0; positive boosts/negative
   bury values are lexicographic, never summed. Hides across all active scopes
   always veto. Duplicate/empty rule IDs fail validation. Response
   `active_rule_ids` is unique lexicographic ascending, not request order.
4. Supplied personalization factors each must be finite in [0.25,4]. Matching
   factors are sorted numerically, composed with Neumaier-compensated log
   summation, **clamped once** to [0.25,4], then quantized to 12 decimal
   places. This explicit resolution prevents tiny cancellation errors from
   breaking neutral-score ID ties; sub-1e-12 factor differences are not supported. Missing/empty means neutral 1, with diagnostic; no online factor
   producer/cache/timeout service exists. Factors cannot cross bucket/group
   boundaries. Rejected NaN/Inf/out-of-range values never silently default.
5. Products: group only after full eligibility/ranking; choose comparator-best
   eligible variant, output `product_id`, `selected_variant_id` and complete
   `matching_variant_count`. `num_found` is distinct eligible products.
   Variants: output both IDs; count is eligible variants; matching count=1.
6. Pins only claim eligible candidates. Stronger query/category/global scope,
   then priority, then ID wins; exact ties keep first organic-ranked candidate.
   Choose one strongest pin per grouped product. Product-target pin displays
   its comparator-best eligible variant. A **winning explicit variant-target
   pin displays that exact eligible variant**; if its slot claim loses, the
   product remains organic with its original best variant. Count/facets do
   not change. Position is zero-based absolute before pagination. An eligible
   pin with position >= complete result count is an **error**, never clamped.
   Same-slot loser stays organic, with diagnostic; no shift/retry/duplicate/hole.
   An ineligible/nonexistent target is ignored, including its unusable position.
7. Explicit price sort with `shopper_overrides` disables pins/groups/personal
   ranking, keeps hides/filters/facets and price-sorts before product selection.
   `merch_overrides` is a separate experiment: normal comparator stays first,
   requested price is a subsort, pins apply. Neither policy claims full Athos
   compatibility. No random or hidden fallback sort is installed.
8. Facets self-exclude **only their own user filter field**, preserving all
   other hard restrictions, lexical membership, stock and hides. Product mode
   deduplicates product IDs per bucket; a product may count in multiple buckets.
   MultiEnum repeated values count once. Numeric -0 and +0 share bucket `0`.
   Missing values have no bucket. Full facet maps precede pagination.

## Evidence and instrumentation

Independent Rust scan oracle does not call the native index/candidate helpers.
Tests cover sibling safety, full set grouping/pagination, product/variant counts,
self-excluding facets, rank-100 promotions, group precedence, lexical coexistence,
finite/bounded factors, pin eligibility/conflicts, strict schema and BM25 seams.

Response metrics: catalog/lexical/structural/verified/eligible/ranked variant
counts, distinct eligible products, facet rechecks, elapsed wall microseconds.
JSON uses serde_json `float_roundtrip` to preserve full f64 ingestion bits.
Engine separately reports build duration. These are diagnostics, **not CPU,
RSS/PSS, cost or quality evidence**. External same-workload process measurements
must include the BM25 index and HTTP serialization/queueing, factor acquisition,
updates/rebuild overlap and required services. No performance cutoff optimization
has been applied; exact all-candidate ordering is intentionally the baseline.

## Unsupported / pending (not counted as covered)

Synonym management, typo/zero-result fallback, autocomplete, product-intent
understanding, arbitrary Boolean/multiselect filter DSL, redirects, aggregate
behavior learning, real personalization production/cache/tracking, timed/geo/
segment/A-B campaigns, rich merch UI/banners, multi-tenant ACL/config service,
channel/multi-currency price, optional/missing numeric sort, realtime updates,
production HA/security, and all carousel/bundle/you-may-also-like profiles.
Coverage requires approved weighted scenarios and quality gates; counting these
unit tests is not an “80%” metric. No 20% cost or TCO conclusion follows.

## v1.1.1 provenance correction (runtime remains v1.1)

**We previously misattributed serialized TSV field strings as official decoded
WANDS query values. That attribution was wrong and is corrected here.** The
legacy workload's naive tab splitting retained CSV wrapper quotes and doubled
quote escaping for query IDs 208, 285 and 391. An exact copy of a flawed workload
is not equivalent to the official decoded query text.

The pinned official `query.csv` is tab-delimited **with CSV quoting**. Its full
SHA256 is `63b61660560fecc33ec490804c7e2b81402ee3e7c31a9cbb5e03736639f68e95`
at [WANDS commit 3b74dcf](https://github.com/wayfair/WANDS/blob/3b74dcf4ba29ab8ff3e6a50b5b09fc627cb882b5/dataset/query.csv).
Correct loading uses `csv.DictReader(file.open(newline='', encoding='utf-8'),
delimiter='\t')` with standard double-quote decoding, not `line.split('\t')`.
Decoded values are `fawkes 36" blue vanity`, `48" sliding single track , barn door
for laundry`, and `writing desk 48"` respectively. Genuine inch quotes remain;
transport quoting is decoded, not sent as part of the shopper query.

The old `tests/fixtures/wands_raw_query_regressions.json` filename/content is
retained byte-for-byte as historical evidence, but its strings are now labeled
**legacy naive-TSV robustness inputs, not official decoded queries**. A separate
`wands_official_decoded_query_regressions.json` records the correct values,
source/reader hashes, and an exact three-record official source excerpt. The
bundled `scripts/athos80_verify_query_provenance.py` verifies this decoding and
shows exactly how naive splitting produced the old strings. The new Rust test
checks the correctly decoded values without changing them inside the engine.

The historical strict-profile run stopped after 824 successful checks on its
legacy workload. v1.1 added explicit `bm25_literal`; strict `bm25` remains
unchanged. This revision does not change either implementation or any serving
behavior. Earlier wrong-source workload results must not be promoted as official
WANDS evidence. Corrected corpus/golden/performance runs recorded new input
hashes and reran all 1,924 checks; see the experiment report. Historical measured
results remain separate from validation of a newly compiled PR checkout. No query is dropped to repair the provenance error.
