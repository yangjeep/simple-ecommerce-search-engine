# E2c Adversarial Review — Findings

Read directly: `ISSUE45_PROTOCOL.md` (full), `e2c_schema.rs`, `e2c_canonicalizer.rs`, `e2c_majority_vote.rs`, `e2c_compile.rs`, `e2c_metrics.rs`, `e2c_adversarial_fixtures.rs`, both eval binaries, both `run1` artifact pairs, the disagreement-taxonomy artifacts, and the relevant `ISSUE42_LOG.md`/`ISSUE42_PROTOCOL.md` E2b sections. Also inspected `git log`/`git show` on the E2c commits.

## CONFIRMED

**1. Treatment D never diverges from Treatment C on any real measured data — its distinguishing mechanism is validated only by a synthetic unit test.** `summary.json` "treatments": C and D report byte-identical `n_promoted` (42/53), identical `stability` (100.00% on every axis), and identical `retrieval_significant_recall_pct` (89.47%). Cross-checking against `e2c_canonicalizer.rs:229-252` (D's majority-vs-plurality bar) and the raw-run data in `per_key_detail.txt`, every real unstable key has a landslide role split (4-1 or better) — none falls in D's actual decision zone (34–50% support). D's only demonstrated behavioral difference from C is the synthetic test `conservative_treatment_abstains_below_true_majority` (`e2c_canonicalizer.rs:601-620`). The GO gate (`main_run1.txt:47-48`) reports D passing all five criteria identically to C, which is true but empirically vacuous — D's core safety claim ("stricter admission bar catches more") is untested by real data in this checkpoint. Confidence: high.

**2. The "evidence-based" rules R3/R4, on every real key they touch, produce the same answer plain plurality/majority voting of the raw proposals already would have produced — their real leverage is leave-one-out stability, not correcting a wrong vote.** `cross_run_type_conflict` (`e2b_validator.rs:197-206`) only fires Enum/Boolean-vs-Numeric, so R3 (`e2c_canonicalizer.rs:181-224`) can *only* ever engage on a genuine numeric/categorical split. Across all 21 raw-unstable keys (`per_key_detail.txt`), that happens exactly once: `thread_size` (automotive), where the raw split is 4 Enum / 1 Numeric (`per_key_detail.txt:409-419`) — a plain plurality already yields Enum without R3. `productwarranty`/`warrantylength` (also in the "value_type_ambiguity" taxonomy bucket) are Enum-vs-FreeText, which R3 structurally cannot touch and which the codebase's own adversarial-fixture comment (`e2c_adversarial_fixtures.rs:351-357`) admits are "resolved by ordinary plurality... not by R3." Likewise R4's showcased case, `voltage`, has raw *primitive* votes of 2 `numeric_range` / 3 `none` (`per_key_detail.txt:488-498`, matching protocol §4's own disclosed count) — a plain primitive-plurality vote already picks `none`. So on this dataset, R3 fires on one key and changes nothing a vote wouldn't already give; R4's showcased case is likewise vote-concordant. Where R1/R6 *do* add genuine non-vote value is real (R1 turns fragile 3-2 primitive splits into landslide-role-derived, leave-one-out-stable answers; R6 unconditionally overrides the 158-pair scope-disagreement pool that no vote resolves at all) — so the claim "C ≠ B in disguise" survives, but it survives almost entirely on R1+R6, not on R3/R4/R7's touted evidence-based arbitration, which this real dataset barely exercises. Confidence: high.

**3. GO-gate criterion 5's boolean ignores its own reliability flag.** `go_gate_for()` (`e2c_canonicalization_eval.rs:582-610`) takes `c5_relevance_within_5pct` as a plain bool and never consults `e2e_check_reliable`. The actual run shows `check_reliable: false` (near-floor NDCG, `summary.json:44-53`) yet `c5(relevance within 5%)=true` is counted toward the "GO" verdict (`go_gate.C = [true,true,true,true,true]`). This is a real, structural gap between "criterion 5 passed" and "criterion 5 was measurable." Severity is mitigated: this exact pattern (PASS-with-caveat on unreliable near-floor NDCG) is inherited verbatim from E2b, was previously flagged and reviewed there (`ISSUE42_LOG.md:2156-2265`, "Confirmed defect... both reviewers, independently"), and the caveat string is printed alongside every PASS in both `main_run1.txt:44` and the JSON. Not novel or hidden — but still a real gap in the gating logic itself, not merely in reporting. Confidence: high.

**4. The "SINGLE-RUN" stricter self-check is not part of the preregistered §9 design and the formal go_gate does not incorporate it — but it is not buried either.** Grepping `ISSUE45_PROTOCOL.md` for "single-run"/"SINGLE-RUN" finds zero hits; the design in §9 is leave-one-out only. The single-run reading (95.20% full/primitive agreement, failing the 99%/98% bars) was added in the implementation binary post-freeze (`e2c_canonicalization_eval.rs:249-281, 644-664`) and is explicitly excluded from `go_gate`/`gate_by_treatment` — it's reported separately as `go_gate_single_run_stricter_reading`. It is printed as the *second* line of console output (`main_run1.txt:10`) and is present in full in the JSON, so it is not concealed in this artifact. The risk is prospective: nothing in the codebase forces any future summary/decision document to carry this caveat forward; if a downstream `SCALE_UP_DECISION.md`-style document quotes only "100% canonical stability," the 95.20% single-run number would then be effectively buried even though it isn't buried here. No such downstream document exists yet in this repo. Confidence: high on the mechanism, medium on future risk.

**5. `pairwise_stability`'s two-Abstain-counts-as-agreement convention is real and is, by construction, gameable — but was not exploited in this run.** Confirmed at `e2c_metrics.rs:150-157` and its own test (`e2c_metrics.rs:241-257`). A treatment that abstained 100% of the time would trivially score 100% stability under this metric. In practice, Treatment C's abstention (20.75%) is only modestly above B's (13.21%), and retrieval-significant recall stayed at 89.47% — *above* E2b's own 86.84% floor, comfortably inside the joint recall/abstention guard the protocol pre-declared for exactly this failure mode (§12: "a treatment that abstains its way to 100% stability... fails this even if criteria 2/3 pass"). So the guard exists, is exercised, and passes. One real gap: the JSON reports aggregate stability and aggregate abstention but never breaks down how many of the 11 "unstable→now_stable" keys became stable via `Promoted` vs via `Abstain`-vs-`Abstain` agreement — so I cannot fully rule out abstention driving a meaningful share of the *specific* 11/11 conversion number, only the aggregate 100%/recall picture. Confidence: high on the mechanism, medium on the "not exploited" conclusion for the conversion-rate metric specifically.

**6. Arithmetic re-verification — no errors found.** Recomputed by hand from `summary.json`: B abstention `1 - 46/53 = 13.2075%` ✓; C/D abstention `1 - 42/53 = 20.7547%` ✓; B recall `37/38 = 97.3684%` ✓; C/D recall `34/38 = 89.4737%` ✓; stable-but-wrong `2/11 = 18.18%` ✓; raw combined-metric `937/1250 = 74.96%` — this cross-validates against the *independently written* `scripts/e2c_disagreement_taxonomy.py`'s own output (`disagreement_taxonomy_run1/summary.txt:31`, "313/1250 (25.04%)" complement), a genuine two-implementation agreement, not a single miscomputed pipeline. Serving-overhead P95/P99 overheads recomputed from raw ms values matched to printed precision. All GO-gate booleans recomputed from their stated thresholds matched. Confidence: high.

## RULED OUT

**A. Oracle leakage — ruled out.** `grep -rn e2b_oracle crates/issue42-eval/src` shows it referenced only in `e2c_canonicalization_eval.rs:161-162` (after-the-fact scoring) and `e2b_pipeline.rs`/`e2b_workload.rs`/`lib.rs` (pre-existing E2b infrastructure). Zero references in `e2c_canonicalizer.rs`, `e2c_majority_vote.rs`, or `e2c_compile.rs`. Matches the protocol's own disclosed design.

**B. R3 threshold reverse-engineering — ruled out.** `R3_BOUNDED_CARDINALITY=50` is loose relative to its one real trigger (`thread_size`, distinct=3) — a tightly data-fit threshold would sit close to 3-10, not 50; the constant is generously round, consistent with a principle-first choice, not curve-fitting to a specific disagreeing key. Baseline SHA/rule commit structure is plausible per the commit message, though see the git-history caveat below.

**Rule-ordering / boundary bugs (E) — ruled out on inspection.** Traced `canonicalize()`'s full control flow (R2→R3/R9→D-bar→R5→R7→R6→R1→R4→R10/R11→R8): R7's early return correctly bypasses R6 (matching §4's own "Scope::Relationship never assigned by R6" disclosure); R4's primitive/significance override correctly runs after R1 computes primitive; D's bar correctly excludes Relationship (caught downstream by R7 regardless); R3's threshold boundaries (`<0.5`, `>=0.9`, `<=50`) are asymmetric by disclosed design, not off-by-one bugs.

## PLAUSIBLE (unresolved)

**Git-history audit trail is too coarse to independently verify "no threshold tuning after seeing results."** Only two commits exist for E2c: `291fb71` (protocol freeze) and `c362ed8` (all rule code, all tests, both eval binaries, and both run artifacts, squashed together). The commit message itself discloses an ordering bug (R9 firing before R3) was "caught... before any measurement was trusted" — i.e., at least one iteration cycle happened pre-commit. This is legitimate TDD-style development, not necessarily evidence of misconduct, but it means the protocol's own §1.2 commitment ("no rule edited after seeing a measurement result") cannot be verified from the repository; it rests entirely on the author's self-report. Confidence: medium — a real methodological gap, not a demonstrated violation.
