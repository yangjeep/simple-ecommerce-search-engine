## Findings

**1. R3 minority-vote hijack bug — CONFIRMED, file:line `e2c_canonicalizer.rs:193-224`**
`any_conflict` is computed over *every* pair of the (up to 5) raw proposals, not just proposals sharing the current R2 plurality role. When triggered, R3 unconditionally overwrites `role` to `Enum`/`Numeric` based on catalog stats, with no check that the plurality winner was ever Enum or Numeric. I verified this empirically with a controlled unit test (temporarily added, run, then reverted): 3 non-abstaining `FreeText` votes + 1 `Enum` + 1 `Numeric` (a clean 3/5 FreeText plurality) canonicalizes to `Enum` with confidence 0.2 (1/5 actual support), silently discarding the real majority. This contradicts the protocol's own §4 description of R3 as resolving "Enum-vs-Numeric... role votes split," and the code comment ("R3 tries to resolve it... first") doesn't disclose that R3 fires independent of what R2 actually decided. **Scope check**: I confirmed via script that none of the 20 real frozen artifacts across all 4 configs contain a (config,key) group meeting this bug's trigger condition (FreeText/other plurality + coexisting Enum-minority + Numeric-minority), so the reported 100% GO-gate numbers are not affected by it — but the rule as shipped is unsound and could silently misclassify future data with high confidence rather than abstaining.

This is legitimate scoring, not decision leakage.

**3. Rule constants postdictively fit to already-seen disagreement — PLAUSIBLE, `ISSUE45_PROTOCOL.md:26-70` + `e2c_canonicalizer.rs:40-47`.** Commit `291fb71` freezes the protocol *and* the disagreement-taxonomy artifacts (`scripts/e2c_disagreement_taxonomy.py`, `per_key_detail.txt`) in the same checkpoint — §1 itself discloses "there is no config or run subset this document can honestly call never seen." `R3_BOUNDED_CARDINALITY=50` is justified in prose as chosen "to cover exactly" the observed cases (thread_size=3, color=4686) — a very wide margin, so that specific constant looks robust rather than narrowly reverse-engineered. But `compatibledrainassemblypartnumber` (distinct_values=78, the one real "insufficient evidence" case) sits just above 50, and its correct (disclosed-as-desired) behavior — abstain rather than silently demote to Enum — depends on the constant being below 78; this dependency is never mentioned in the constant's own stated justification. Not proven to be deliberately gamed (the protocol's honesty about the non-blind design is exemplary), but the "principle-derived, not data-fit" claim is weaker than stated for this boundary case.

**4. R2 plurality does almost all of the real work on role; R1/R6 do the rest — CONFIRMED via direct arithmetic on `main_run1.txt`.** Comparing Treatment B (naive plurality, no R1/R3-R8) against Treatment C under the *identical* leave-one-out methodology: role stability B=99.68% vs C=100.00% — only a 0.32pp gap, meaning R3/R4/R5/R7 together barely move role-level stability beyond plain plurality voting; B's own plurality is nearly as stable as C's "evidence-based" resolution. The ~18pp gap in *full* agreement (B=81.68% vs C=100%) is structural, not emergent: (a) R1 makes `primitive` a pure function of `role` and (b) `value_type_for_role` makes `type` a pure function of `role` too, so those two "independent" comparison axes collapse into role once R1 is applied (matches the protocol's own claimed 65.2%-of-disagreement contribution — legitimate); (c) R6 hardcodes `scope=Product` as a dataset-wide constant whenever `has_real_variant_grouping=false` (always true in this run) — this is *tautologically* 100% stable by construction, not a resolved disagreement, contributing ~14pp (B scope=85.92% vs C=100%) essentially for free. This is disclosed in the protocol (R6, §6) but the "100% full agreement" headline folds in this trivial, disclosed-but-underweighted contribution alongside R1's genuinely earned one.

**5. Abstain-Abstain counted as agreement — PLAUSIBLE but not exploited here.** `e2c_metrics.rs:150-157` counts two `Abstain` outcomes as agreeing on every axis. In principle a treatment could game "100% stability" purely by abstaining everywhere. Traced one real example (`compatibledrainassemblypartnumber`): under every leave-one-out drop, role resolves to `Identifier` and R5's fixed-stats gate (uniqueness 0.4845 < 0.95, distinct 78 > 50) forces `Abstain` regardless of vote count — genuinely deterministic, not opportunistic flip-flopping. C's abstention rate (20.75%) isn't extreme, and recall (89.47%) stayed *above* the E2b baseline (86.84%), so the falsification criterion in §12 ("abstains its way to 100% stability on a shrunken accepted set") is not triggered by this run's numbers. Convention is a real soft spot in the metric design, not a demonstrated gaming instance.

**6. 95.20% single-run number is not part of the machine-readable GO decision — CONFIRMED, `bin/e2c_canonicalization_eval.rs:619-637` vs `:649-664`.** The `go_gate` JSON field (what an automated pipeline would consume) is computed only from the lenient leave-one-out design and shows all-true. The stricter single-run self-check (role/primitive/full = 95.20%, failing c2/c3's 99%/98% bars) is computed and reported separately in `go_gate_single_run_stricter_reading`, never merged into `go_gate`. This design isn't part of the frozen protocol (`ISSUE45_PROTOCOL.md` never mentions "single-run") so it's a bonus check, not a violated preregistration. It is **not buried** in the human-readable output — it's printed prominently, second line of the stability section, with its own labeled section and explicit FALSE booleans — and no `SCALE_UP_DECISION.md`/decision doc yet exists for E2c that could misrepresent it. But a consumer reading only `go_gate.C` sees unqualified GO with no structural link to the caveat.
