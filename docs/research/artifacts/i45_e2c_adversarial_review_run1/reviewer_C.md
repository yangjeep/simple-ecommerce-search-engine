## A. Oracle leakage — RULED OUT
`grep -rn e2b_oracle` across every `e2c_*.rs` file finds it **only** in `bin/e2c_canonicalization_eval.rs:161-166`, populating `oracle_by_key`/`oracle_all` used strictly downstream for `unsafe_accepted_count`, `retrieval_significant_recall`, and the stable-but-wrong check — all after `canonicalize()`/`majority_vote()` have already produced an outcome. Neither `e2c_canonicalizer.rs`, `e2c_majority_vote.rs`, nor `e2c_compile.rs` imports it. Confidence: high.

## B. Self-grading / optional stopping — MIXED
R3's constants (`R3_BOUNDED_CARDINALITY=50`, `R3_LOW_PARSE_RATE=0.5`, `R3_HIGH_PARSE_RATE=0.9`, `e2c_canonicalizer.rs:45-47`) match the protocol's own stated derivation (`ISSUE45_PROTOCOL.md:216-233`) with wide margin from the one real boundary case (`color` at 4,686 distinct vs. the 50 ceiling) — no evidence of curve-fitting to a specific data point. **RULED OUT** for that mechanism.

However, the "SINGLE-RUN (stricter self-check)" design (`e2c_canonicalization_eval.rs:251-280`) that reports 95.20% is **not in the frozen protocol** — `grep -in "single-run"` on `ISSUE45_PROTOCOL.md` returns no hits outside an unrelated sentence at line 344. It was added during implementation, not preregistered. It works *against* self-interest (it fails c2/c3 and is reported, not suppressed), so this isn't gaming toward a favorable result, but it is a real preregistration-discipline gap: an unregistered, harder test was substituted in as a "self-check" after the primary design was already fixed. **PLAUSIBLE**, moderate severity, mitigated by honest reporting.

## C. Hidden majority voting — CONFIRMED (with important nuance)
I instrumented the actual crate code (temporary binary, later deleted) to test whether R3's evidence override ever changes an outcome versus plain R2 plurality. Result: `cross_run_type_conflict` (`e2b_validator.rs:197-206`, Enum/Boolean-vs-Numeric only) fires on exactly **1 of 125** (config, real-key) groups in the entire 20-artifact dataset (`automotive/thread_size`), and even there the final role is **identical** to what plain plurality alone already gives (Enum wins 4/5 regardless of R3). So R3 — the rule the protocol showcases most (`ISSUE45_PROTOCOL.md:215-233`, with its own dedicated unit test at `e2c_canonicalizer.rs:487-504`) — never once changes a real outcome in this dataset; it is empirically inert here.

This directly contradicts the protocol's own §6 claim that `productwarranty`/`warrantylength` (Enum-vs-FreeText cases) are "resolved by R3" (`ISSUE45_PROTOCOL.md:426`): `cross_run_type_conflict` structurally cannot fire for Enum-vs-FreeText, so those cases are resolved by plain R2 plurality alone. This is confirmed not just by my instrumentation but by the implementation's **own** test comment: `e2c_adversarial_fixtures.rs:355-357` explicitly states the warrantylength-shaped case is "resolved by ordinary plurality... not by R3, which only ever engages a real Enum-vs-Numeric role split" — directly contradicting the protocol prose it's supposed to support.

That said, Treatment C is **not** merely Treatment B under a different name: R1 (primitive-is-a-function-of-role, `e2c_canonicalizer.rs:52-60`) provably accounts for essentially all of the primitive/full-stability gap between B (92.80%/81.68%) and C (100%/100%) — B votes primitive directly while C never lets it vary independent of role. R6 (scope hard-defaults to Product, `e2c_canonicalizer.rs:294-301`) similarly forces 100% scope agreement by discarding the vote entirely rather than resolving it, which is disclosed (`ISSUE45_PROTOCOL.md:260-270`) but is a hard override, not "evidence-based resolution." R7 (Relationship hard-block) and R5 (Identifier statistical bar) each demonstrably prevent one real unsafe promotion Treatment B would have made (color/wands_anonymized → Relationship; compatibledrainassemblypartnumber → Identifier at uniqueness 0.48). **Net verdict: C's real advantage over B comes from R1/R5/R6/R7's hard, non-vote mechanisms — not from R2/R3's touted "evidence-based role resolution," which in practice just replicates plain plurality.** Confidence: high, directly measured.

## D. Stability via excessive abstention — LARGELY RULED OUT
`pairwise_stability` (`e2c_metrics.rs:150-156`) does count two Abstains as agreeing on every axis. I measured how much this convention actually drives the headline 100%: of the 27 raw-unstable (config,key) groups (across all 4 configs) that became leave-one-out-stable under Treatment C, **25 stabilized via genuine identical Promoted answers and only 2 via the Abstain-Abstain convention** (`wands_anonymized/color`, `wands_anonymized/compatibledrainassemblypartnumber` — both real, defensible abstentions per R7/R5, not gaming). That's ≈1.6% of the 125 total measured groups. The convention is a real methodological soft spot worth flagging (**PLAUSIBLE** as a design concern in the abstract), but it is not what produced this run's 100% figure. Separately: C's abstention rate is real and costly — 20.75% (11/53, `main_run1.txt:32`) vs. B's 13.21%, and recall dropped to 89.47% (34/38) vs. B's 97.37% (37/38), leaving only 2.63pp of headroom on GO-gate criterion 4's 5pp allowance — this tension is disclosed and gated per the protocol's own falsification criteria, not hidden.

## E. General correctness
**E1 — CONFIRMED, real bug in the reviewed commit `c362ed8`.** The R3/R9 `any_conflict` check (`e2c_canonicalizer.rs:193-194` pre-fix) scanned **every** pair of the 5 raw proposals for a categorical-vs-Numeric conflict, without requiring either side to be the actual R2 plurality winner. This means an unrelated minority pair (e.g., 1 Enum + 1 Numeric vote sitting alongside a 3/5 FreeText plurality) could silently hijack and overwrite the real plurality winner. I verified independently (own instrumentation, run before I noticed any change to the file) that this bug happened not to corrupt any of the 125 real (config,key) groups in the actual dataset, because only one group ever had any such conflicting pair at all, and it already coincided with the plurality winner. So `main_run1.txt`'s reported numbers are unaffected, but the rule as shipped was unsound and could misclassify a differently-shaped future input with false confidence rather than abstaining — a genuine correctness defect, later fixed (uncommitted, in the concurrently-modified working tree).

**E2 — CONFIRMED**, see Finding C: `ISSUE45_PROTOCOL.md:426`'s claim that R3 resolves Enum-vs-FreeText cases is false against the actual code.

**E3 — RULED OUT** (boundary/off-by-one): R3's `<0.5`, `<=50`, `>=0.9` (`e2c_canonicalizer.rs:197,206`) match the protocol text (`ISSUE45_PROTOCOL.md:216-233`) exactly.

**E4 — RULED OUT** (buried single-run number): the 95.20% figure is printed in its own clearly labeled section (`main_run1.txt:52-54`) and given an equal-prominence top-level JSON key `go_gate_single_run_stricter_reading` (not nested inside `go_gate`) with `c2`/`c3` explicitly `false`. Not buried — see Finding B for the separate preregistration-timing concern.

**E5 — disclosed, not a defect:** both stable-but-wrong cases (`productwarranty`→Enum, `heat_range`→Numeric, `main_run1.txt:39-40`) are unanimous-raw-vote errors the deterministic layer inherits rather than fixes; correctly reported via the protocol's own "stable-but-wrong rate" metric, not concealed.
