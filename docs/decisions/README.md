| [`ISSUE55_WHOLE_WORKLOAD_DECISION.md`](ISSUE55_WHOLE_WORKLOAD_DECISION.md) | Traffic-weighted re-measurement of the H3 fixes on real `p9_e02` end-to-end traffic: **REFINE** — the isolated 4.6x-8.2x gain does not hold uniformly; root-caused to an unconditional per-candidate `HashMap` lookup the fix added ahead of the old code's zero-work short-circuit for empty-residual/empty-preference queries, confirmed by three independent measurements (an initial cache-locality theory was tested directly and falsified). Hybrid-traffic dilution and a `select_nth_unstable_by` tie-heavy regression were also tested directly and ruled out. Fix scope narrowed, not reverted; hoisting the short-circuit is named as the next experiment. |
| [`ISSUE55_EMPTY_RESIDUAL_FIX_DECISION.md`](ISSUE55_EMPTY_RESIDUAL_FIX_DECISION.md) | The named fix (hoist the emptiness check before the `HashMap` lookup): **KEEP** — regression eliminated (back to pre-Issue-55 baseline on the two known queries), confirmed-win path gains an *additional* 2.5-8.2% from the same reorder, no correctness change. Whole-workload `structural_routed` aggregate returns to ~2.48x, essentially the original pre-Issue-55 baseline — explained, not a disappointment: independently confirmed to be dominated by `index.execute()`/`lookup_variant` candidate-materialization cost no Issue #55 fix targeted, not by scoring/sorting (now measurably cheap). Closes the text-token-cache checkpoint's regression addendum; names a planner-policy follow-up (should 100%-of-catalog candidate sets route to `FastPath` at all) as still open. |
| [`ISSUE55_AMBIGUOUS_ROUTING_DECISION.md`](ISSUE55_AMBIGUOUS_ROUTING_DECISION.md) | Investigated whether the planner discards preserved query ambiguity (`plan()` never reads `query.ambiguous`) — found a real, mechanistically-confirmed local effect (n=4 real WANDS queries, -65.51% NDCG gap), but **REJECT/SUPERSEDED** as a new finding: an adversarial-review workflow found this exact question was already answered at ~100x scale by `PHASE3_DECISION.md` ("ambiguity supplies no ranking signal") and already partially solved by a sibling, uncomposed module (`admission::admit`'s `RejectReason::Ambiguous`). Whole-workload impact negligible (~0.45pp). Folded into `ISSUE55_EMPTY_RESIDUAL_FIX_DECISION.md`'s existing follow-up and a `PHASE3_DECISION.md` addendum rather than treated as new work. Preserved as a positive example of adversarial review catching an overclaim before it was recorded as a decision. |
| [`ISSUE51_FULLGATE_SCALE_DECISION.md`](ISSUE51_FULLGATE_SCALE_DECISION.md) | Reran R1/Issue #42's full `<=5%` `execute_planned` overhead gate at realistic (~43,000-product) catalog scale, closing `ISSUE51_DECISION.md`'s own named next step. **REVISE, confirmed not resolved**: Treatment E still fails the bar (14.0%-16.7% across 3 runs, essentially unchanged from R1's original N=5 measurement) — the registry mechanism's own asymptotic advantage is real but was never the dominant cost; a per-row breakdown found the actual driver is the `Punt` fallback's lexical-delegate query cost for genuinely ambiguous, uncorroborated queries, untouched by Issue #51's optimization. Two real methodology defects (decoy attribute pollution collapsing NDCG; a decoy price collision turning a regression-guard row into an accidental 97%-of-latency full-catalog scan) were found and fixed before trusting any number. |

## How to read old numbers

Decision records are intentionally not rewritten to make the research look linear. When an experiment later discovered a methodology defect, the repository preserves the old result and records the correction. A later decision may therefore supersede an earlier interpretation without deleting it.

For current project status, always prefer the root [`README.md`](../../README.md) and [`../architecture/README.md`](../architecture/README.md) over an old phase narrative.
