# Round 1 Experiment Log

Append-only, continuing the format from `docs/experiments/LOG.md` (E000-E007,
"Phase 0"). Phase 0 established that the commerce-native architecture is
internally coherent on deterministic, hand-authored fixtures. It did **not**
establish real-world coverage, precision, competitiveness, or relevance.
Round 1's job is to attack those specific gaps with the most realistic
evidence this environment can obtain. Do not read a Round 1 entry as
correcting a Phase 0 entry; if evidence contradicts an earlier entry, a new
entry says so — nothing here is rewritten.

Every entry generalizes the Phase 0 template with two required framing
fields:

- **Evidence class** — `real` (public dataset, human judgments, external
  system), `synthetic` (generated, seeded, explicitly not a relevance
  claim), or `hand-authored` (small fixture, correctness-only). Any metric
  not tagged `real` must not be cited as evidence of real-world coverage,
  precision, or comparative performance.
- **Independence** — for any coverage/precision number, whether the query
  set and the semantic context being measured were built independently of
  each other. A number is not independent evidence if the query set was
  generated from the same ontology/lexicon being scored against it.

   `archive.org`, `zenodo.org`, and generic `codeload.github.com`

Downloaded and SHA-verifiable via the file's own commit content:
`shopping_queries_dataset_products.parquet` (1,108,857,465 bytes) and
`shopping_queries_dataset_examples.parquet` (51,286,808 bytes). Kept in

**Real US-locale catalog**: 1,215,854 distinct products (`product_id`,
`product_title`, `product_description`, `product_bullet_point`,
`product_brand`, `product_color`). No price, no category, no product type,
no structured attributes of any kind beyond brand/color — see R1-E01 for
what this means for the thesis.

**Real US-locale query judgments (test split)**: 22,458 distinct shopper
queries, 425,762 query-product judgment pairs, each labeled by human
annotators as one of Exact / Substitute / Complement / Irrelevant (ESCI).
The `test` split (not `train`) is used throughout Round 1 — the dataset's
own held-out evaluation partition, chosen because nothing in this project
trains on it, so there is no train/test leakage question to even raise.

This is real, independent, human-labeled, third-party data: it satisfies
every ground rule in the Round 1 brief ("prefer real public data," "keep
query-source labels," "do not evaluate the semantic compiler only on
queries generated by the same compiler or ontology," "use

## R1-E01 — Real catalog ingestion, profiling, and scale ladder at 1.2M products

**Evidence class**: real (ESCI US-locale catalog). **Independence**: n/a (a
profiling measurement, not a coverage/precision claim).

**Question**  
Does the typed domain model built in Phase 0 (Product/Variant with
required `product_type`/`category`/`price` fields) fit a real, large-scale
ecommerce catalog without modification, and what does real ingestion at
1.2M products cost in build time, memory, and index size — extending
Phase 0 E007's synthetic scale ladder (which stopped at 100k synthetic
products) with real data past its own "1M if the environment permits"
target?

**Hypothesis**  
(a) The real ESCI catalog will show meaningful missingness and
normalization collisions in brand/color fields (real messiness, not
assumed away). (b) `commerce_core`'s domain model, unmodified, cannot
represent this catalog faithfully — no source field exists for
product-type, category, or price at all — requiring an ingestion-side
design decision (sentinel values vs. a domain-model change), which is
itself evidence about how "typed-first" the architecture can be in
practice. (c) `CatalogIndex::build` at 1.2M real products stays within
this environment's resources (15 GiB RAM) and produces a build time in
the tens of seconds to low minutes, not hours. (d) Phase 0 E007's
approximate-index-size-vs-RSS gap (≈20% at 100k *synthetic* products)
will persist or worsen at real scale with real (longer, more varied)
text.

**Decision threshold**  
Record real messiness numbers regardless of magnitude (there is no
pass/fail on profiling). For (b), the threshold is binary: does ingestion
require a domain-model change or not, and what does the chosen answer
cost. For (c)/(d), advance-worthy if build completes in this
environment without OOM and the RSS gap is *explained* (Area 5's actual
ask — "explain that gap," not merely restate it) with instrumented
numbers, not hand-waved.

**Dataset**  
Amazon ESCI (see "Dataset and baseline acquisition" above). US-locale
product catalog, deduplicated by `product_id`: **1,215,854 real products**.
No sampling — the full real catalog.

**Workload**  
`crates/round1-eval/src/bin/profile_catalog.rs`: load -> profile -> build
`Catalog` -> build `CatalogIndex`, instrumented with `Instant` timers and
`/proc/self/status` `VmRSS` snapshots at each stage, plus a raw-UTF8-byte
count of every text field (title/description/bullets/brand/color) as a
zero-overhead baseline to compare against measured RSS.

**Implementation**  
`crates/round1-eval`: `data.rs` (JSONL loader), `catalog.rs`
(`build_catalog`: real ASIN -> sequential `ProductId`; brand strings
interned by normalized/lowercased key into `BrandId`; color stored as a
variant-level `Enum` attribute; title/description/bullets as
product-level `Text`), `profile.rs` (messiness profiler). **Design
decision on (b)**: `commerce_core`'s `Product`/`Variant` struct was **not**
changed (required `product_type`/`category`/`price` fields kept
exactly as Phase 0 left them, to avoid touching Phase 0's 33 passing
tests and 7 ADRs' worth of fixtures under this round's time budget).
Every real product instead gets sentinel `ProductTypeId(0)`,
`CategoryId(0)`, `Price::usd(0)` — documented, not hidden; see the
"Interpretation" caveat below for what this decision itself is evidence
of.

**Results** (single run; environment: 4 vCPU Intel Xeon @2.80GHz, 15 GiB
RAM, Linux 6.18.5, rustc/cargo 1.94.1 — same machine as Phase 0):

```

missing_description: 569,795 (46.9%)

  disney(2996), hanes(2783), amazon basics(2652), skechers(2066), generic(1965), columbia(1957), ...

CatalogIndex::build:      61.4-64.0s

                          -> after_index=5,482,656 KB (+3,759,148 KB total)
approximate_size_bytes as fraction of total RSS delta: 7.1%
```

**Interpretation**

(a) **Confirmed, and larger than expected.** 46.9% of real products have
no description at all; 33.4% have no color. Brand-string normalization
(trim + lowercase) removes only 4,929 of 211,156 distinct raw strings
(2.3%) — most of the six-figure brand cardinality is *not* casing/
whitespace noise, it is genuinely six figures of distinct real brand
names. The same holds for color (169,085 distinct normalized values).
Neither Phase 0 fixture (14 hand-authored lexicon entries; Gate 6's toy
catalog with 8 entries) hinted at vocabulary of this scale.

(b) **The domain model does not fit real catalog data as ingested — a
choice had to be made, and the choice made is itself evidence.**
Sentinel product-type/category/price means every real product in this
experiment is structurally indistinguishable from every other on those
three fields. This is not a minor gap: product-type is the single field
CLAUDE.md's own architecture bias names first, and Gate 2's
representative query (`black Nike waterproof running shoes size 9 under
$150`) leans on product-type ("running shoes"), numeric size, and price
— **none of which exist in this real dataset's product records at all**.
Read plainly: a widely-used, real, large-scale ecommerce relevance
benchmark's product catalog does not carry the structured attributes the
Commerce IR's representative query assumes are available. This does not
by itself falsify the thesis (a real production catalog ingestion
pipeline would have a PIM/attribute-extraction stage this experiment
doesn't build), but it is direct evidence that "typed commerce semantics
already exist in the data" is not a safe assumption to carry into Round
1's later experiments — R1-E02 below inherits this limitation (only
brand/color are testable) and should be read with it in mind throughout.

(c) **Confirmed.** 1.2M real products build in ~64s and fit in ~3.8 GB
RSS peak — well within this environment's 15 GiB. No infrastructure
scale-up was required to reach (and exceed) the "target proof" tier with
real rather than synthetic data.

(d) **Confirmed and now explained, not just restated.** The
`approximate_size_bytes` metric (259 MB) accounts for only 7.1% of the
measured RSS delta (3.76 GB) — *worse* than Phase 0 E007's ~20% at 100k
synthetic products, because real text is longer and more varied (1,150
bytes/product of raw source text here vs. a few dozen bytes/product in
Gate 0's synthetic generator). Decomposed:
- Raw UTF-8 text payload: 1,333.81 MB.
- Catalog struct (Product/Variant/String/BTreeMap storage) RSS: 2,955 MB
  — a **2.2x multiplier over raw text**, plausible and explainable as
  `String` heap-allocation overhead (allocator header + padding per
  allocation, and every product has 3-5 separate `String`/`AttributeMap`
  allocations) plus `Vec<Variant>`/struct padding. Not alarming on its
  own.
- Index-only RSS on top of the catalog: ~785 MB, of which the
  bitmap/vector payload (`approximate_size_bytes`) is 259 MB (33%) and
  the remaining ~526 MB (67%) is unaccounted for by that metric —
  plausibly `HashMap` bucket over-provisioning plus **duplicated**
  `String` keys (every `(attribute, value)` bitmap and the
  `lexical_postings` map re-store the attribute/value/token strings as
  hash keys, on top of the copies already living in the catalog's
  `AttributeMap`s).

Per Area 5's explicit "only after measurement should you consider
[interning/arenas/...]; retain only if the result justifies complexity"
instruction: **no optimization is implemented here.** The absolute
number (3.76 GB for 1.2M real products with substantial text) is
workable on any real serving host; the gap is explained well enough to
know where a future optimization would need to target (string
duplication between the catalog's own storage and the index's
`HashMap` keys) without needing to build it speculatively now.

**Caveats**  
Two runs of the full pipeline showed catalog-struct-build time varying
24.1s vs. 30.7s (index build varied 61.4s vs. 63.9s) — likely OS-level
page-fault/allocator variance at this memory scale on a shared container,
not repeated enough (Area 5 wants variance identified; two runs is a
start, not the "repeated noisy measurements" the brief's Engineering
Quality section asks for — a limitation carried into
`ROUND1_SCALE_UP_DECISION.md`). `approximate_size_bytes`'s 67%-unexplained
remainder is a plausible mechanism, not a line-by-line proven one — a
real allocator profiler (e.g. `heaptrack`/`valgrind --tool=massif`) was
not run; not available/attempted in this environment this round.

**Regression check**: none yet — this is a one-off measurement binary,
not a CI-gated test. `crates/round1-eval` has no test suite of its own
(everything in it is an experiment harness over `commerce_core`, which
keeps its own 33 tests green — confirmed via `cargo test --workspace
--all-features` after every change in this round, including the
`SemanticLexicon` fix below).

**Next question**: R1-E02 — with the domain model's sentinel-field
limitation now explicit, what fraction of *real* shopper queries can
brand/color structural extraction alone resolve, and how often is that
extraction actually correct against real human relevance judgments?

## R1-E02 — Real query classification, Semantic FIB hit rate, and semantic precision

**Evidence class**: real (ESCI US-locale test-split queries + human ESCI
judgments). **Independence**: yes — the query set and its relevance
labels are Amazon's own held-out evaluation data, produced independently
of this project; the lexicon is derived from catalog data via
`commerce_core::cold_start` (Gate 6, unmodified) rather than hand-typed
to match these queries.

**Question**  
What fraction of 22,458 real, held-out shopper queries can a
catalog-derived lexicon resolve deterministically (Semantic FIB hit
rate), and — the question Phase 0 never had the data to ask — when the
compiler *does* claim a structural resolution, how often is that
resolution actually correct against real human relevance judgments
(semantic precision), and how much of the truly relevant result set
would a hard structural filter built from that resolution actually
retain (filter recall)?

**Hypothesis**  
(a) A lexicon derived by running Gate 6's `CatalogProfile`/`compile_lexicon`
against the real 1.2M-product catalog (one entry per distinct brand/color
value, no hand-curation) will resolve a non-trivial fraction of real
queries deterministically. (b) Given R1-E01's finding that this dataset's
`color` field is frequently not a genuine color (only brand and color
are extractable at all — see R1-E01), naive one-entry-per-value lexicon
construction at six-figure vocabulary scale will show a **materially
higher ambiguity rate** than Phase 0's tiny hand-curated lexicon (which
had exactly one deliberately-planted collision). (c) Precision (fraction
of filter-passing judged products that are actually relevant) will be
respectable when the filter is satisfied at all, but filter recall
(fraction of relevant products that survive the filter) will be low if
the compiler's single-value-per-attribute assumption is violated by
noisy real "color" data feeding multiple simultaneous, possibly
conflicting, `color` constraints into one query's compiled AND-filter.

**Decision threshold**  
Semantic FIB hit rate: report the real number, no target (a-priori
threshold-setting here would just be picking a number to feel good
about). Precision: a value materially above the base rate of relevant-
vs-irrelevant judgments in the test set would support "structural
resolution correlates with relevance"; materially below would reject it.
Filter recall: this is the sharpest test in the whole round for
"aggressive guessing... is a regression" — if recall is catastrophically
low, that is evidence the *filtering semantics* (hard AND across every
extracted value), not merely the lexicon's vocabulary, needs to change
before any coverage number can be trusted as a serving-time claim.

**Dataset/workload**: R1-E01's real 1,215,854-product catalog; real ESCI
US test-split judgments, 425,762 (query, product, label) rows across
22,458 distinct queries.

**Implementation**  
`crates/round1-eval/src/classify.rs`: `classify()` (7-way execution
category per query, using `ir::compile`'s existing
constraints/ambiguous/residual output plus an exact-ASIN-match check and
a small curated occasion-keyword list — the occasion detector is an
explicitly-labeled heuristic, not a claim of NLP-grade intent
classification); `measure_precision()` (cross-references every
`structural_only`/`structural_plus_lexical` query's compiled constraints
against the real catalog's actual brand/color for every judged product of
that query). `crates/round1-eval/src/bin/query_eval.rs` orchestrates the
full pipeline once (ingest -> derive lexicon -> compile all 22,458
queries -> classify -> measure precision).

**A real performance bug found and fixed along the way**: the first
attempt at this experiment (against a 50k-product catalog subset, ~72k-
entry lexicon) took **28.1 seconds** to classify 22,458 queries — traced
to `SemanticLexicon::max_phrase_words()` (`crates/commerce-core/src/ir/lexicon.rs`)
recomputing `max(phrase.split_whitespace().count())` by scanning *every*
lexicon entry on *every* `compile()` call. Phase 0's largest lexicon ever
exercised had 14 entries, where this was free; at real vocabulary scale
(~375k entries: 206,227 brands + ~169k colors) it made the whole batch
O(queries × lexicon size). Fixed by caching the max incrementally in
`insert()` (no behavior change — verified via `cargo test --workspace
--all-features`, all 33 Phase 0 tests still pass). Effect: the same 50k-
catalog batch dropped from 28.1s to **0.09s** (≈312x); the full
1.2M-catalog / ~375k-entry-lexicon batch (not even attempted before the
fix, given the 50k-scale number) completed in **0.26-0.27s**. Recorded
here per CLAUDE.md's "record failed experiments... do not erase evidence"
— this is exactly a case Phase 0's small-scale fixtures structurally
could not have caught, and Round 1's real-scale data did on the first
real run.

**Results** (single run, same environment as R1-E01; lexicon: 206,227
brand entries + colors derived from `CatalogProfile` over the real
catalog):

```
Query classification (22,458 real distinct queries):
  ambiguous                 8,630  (38.4%)
  structural_only           4,462  (19.9%)
  structural_plus_lexical   7,972  (35.5%)
  semantic_occasion              8  (0.0%)
  lexical_dominant             826  (3.7%)
  unresolved_punt              560  (2.5%)

Semantic FIB hit rate (structural_only + structural_plus_lexical + exact_id_lookup): 55.4%
Punt rate: 2.5%
Ambiguity rate: 38.4%

Semantic precision (structural_only + structural_plus_lexical queries, 12,434 measured):
  precision (filter-passing judged products that are relevant, E+S):  94.5%  (8,811 / 9,321)
  filter recall vs Exact+Substitute ("relevant"):                      4.3%  (8,811 / 205,474)
  filter recall vs Exact only (fairer test — see below):               5.0%  (7,770 / 153,945)
```

Diagnostic (first 10 `structural_only` queries, extracted constraints):

```
"#2 pencils"                 -> [color="#2", color="Pencils"]
"#4 pads without wings"      -> [color="#4", color="Pads", Brand(2081), color="Wings"]
"- horn button without tilt" -> [color="-", color="Horn", Brand(138425), Brand(2081), color="Tilt"]
"0 size 4 pads without wings"-> [color="0", size=4.0, color="Pads", Brand(2081), color="Wings"]
"1 fancy box without lids"   -> [color="1", color="Fancy", color="Box", color="Without Lids"]
"10 gallon camping shower bag" -> [color="10 Gallon", color="Camping", color="shower", color="Bag"]
```

**Interpretation**

(a) **Confirmed, with a caveat that dominates everything else in this
entry.** 55.4% Semantic FIB hit rate looks, in isolation, like a
respectable number — comparable to or better than Phase 0's 55-60%
hand-curated-lexicon figures. It is not comparable evidence of the same
thing. The diagnostic output above shows *why*: "#2 pencils" is being
classified `structural_only` because **both** "#2" and "pencils"
literally appear as `color` field values somewhere in the real 1.2M-
product catalog — i.e. real sellers' data-entry noise (a color field
containing "#2", or "Pencils", or "Without Lids", or "10 Gallon"). The
"structural resolution" this experiment is counting is frequently not a
shopper's brand/color intent at all; it is the compiler matching
essentially arbitrary query words against a lexicon built with **zero
validation** that a catalog field's contents are what its name claims.

(b) **Confirmed, and more severe than hypothesized.** 38.4% ambiguity
rate (vs. Phase 0's single deliberately-planted collision) — at six-
figure combined brand+color vocabulary, accidental word-level collisions
between unrelated catalog entries are the *common* case for query terms
that hit the lexicon at all, not the exception.

(c) **Partially confirmed, but the recall side is a severe, well-
explained negative result — the single strongest falsification-leaning
finding in this round so far.** Precision (94.5%) looks good until its
denominator is understood: it is computed only over the subset of
queries where *some* real product happens to satisfy *every* extracted
constraint simultaneously. The diagnostic output explains why that
subset is small and unrepresentative: `Variant`'s `color` attribute is
single-valued (`AttributeMap`, one entry per key), so a compiled query
requiring `color="Pads"` **and** `color="Wings"` **and** `color="#4"`
simultaneously can *never* be satisfied by any product — it's a logical
contradiction the merged-per-variant matcher (correctly, per Gate 1's
own variant-safety design) rejects outright. Many `structural_only`/
`structural_plus_lexical` queries compile to exactly such
self-contradictory constraint sets, contributing zero matching products
and therefore silently dropping out of both the precision numerator
*and* denominator — while the small remainder (where extraction
happened to be single-valued or coincidentally consistent) is precise.
Filter recall makes the resulting cost visible: even against the
strictest possible comparison (Exact-label-only judgments, ruling out
the "ESCI's Substitute label is generous" alternative explanation), a
hard structural filter built this way **retains only 5.0% of products a
human called an exact match**. Read together: **the naive
"every-catalog-value-is-a-lexicon-entry" cold-start construction,
combined with the existing compiler's implicit assumption that each
structural attribute takes at most one value per query, produces
self-contradictory hard filters on a large share of "resolved" real
queries** — a mechanism, not just a number, and one Phase 0's tiny
hand-curated fixtures (where every lexicon entry really was a genuine,
validated brand/color/product-type value) could not have exposed. This
is not evidence that structural retrieval is worthless; it is direct
evidence that Gate 6's cold-start lexicon construction needs a
**candidate canonicalization / validation step** (Area 9's own phrase,
skipped in Gate 6's implementation) before real catalog field values are
trusted as hard-filter-worthy semantic entities, and that the compiler
needs either conflict detection (reject a self-contradictory constraint
set as ambiguous/unresolved rather than silently compiling it into a
filter that can never match) or a fundamentally different aggregation
rule (e.g. OR-within-attribute, not AND) for multi-source attribute
extraction.

**Caveats**  
Only brand and color are testable at all on this dataset (R1-E01); this
experiment says nothing about product-type/category/price/size
extraction quality, which the source data doesn't support evaluating.
The occasion-query heuristic (20 curated keywords) is coarse — 8 queries
classified `semantic_occasion` is almost certainly an undercount of
genuinely occasion-shaped real queries; not treated as a real metric,
only as a labeled bucket. Single run (deterministic pipeline, so
repeated runs would reproduce identically — no variance to characterize
here unlike E01's timing numbers).

**Regression check**: none yet (see R1-E01). The `SemanticLexicon`
performance fix is covered by `commerce-core`'s existing 33 tests (no
behavior change, so no new test was needed for correctness — a
regression *bench* to prevent this specific bug from recurring at scale
would be a reasonable follow-up, not built this round given time budget).

**Next question**: the recall failure just found is severe enough to

## R1-E02b — Does OR-within-attribute aggregation fix the recall failure? (hypothesis rejected)

**Evidence class**: real (same catalog/queries/judgments as R1-E02).

**Question**: R1-E02 found 5.0% filter recall against Exact-only real
judgments and traced it to self-contradictory `color` conjunctions (a
single-valued attribute required to equal two different values at once).
The obvious fix: aggregate multiple values extracted for the *same*
attribute with OR instead of AND (still AND *across* different
attributes). Does this materially close the recall gap?

**Hypothesis**: OR-within-attribute aggregation will substantially raise
filter recall, since it removes the logical-impossibility failure mode
identified in R1-E02, without materially harming precision.

**Decision threshold**: "materially raise" = at least a few-fold
improvement (e.g. 5% -> 20%+); anything smaller means the aggregation
rule was not the dominant cause and the hypothesis should be rejected in
favor of a deeper explanation.

**Implementation**: `classify::product_satisfies_or_within_attribute`
(new, `crates/round1-eval`, experiment-only — not a change to
`commerce_core`): groups a compiled query's constraints by attribute
(`Brand`, `color`), requires at least one candidate per group to match,
still requires every group that was extracted at all to match. Measured
head-to-head against the existing AND-everywhere rule
(`product_satisfies_and`) on the identical 12,434 queries and their real
judgments.

**Results**:

```
                          existing (AND everywhere)   proposed (OR within attribute)
precision (E+S)           94.5%  (8,811/9,321)         93.2%  (10,551/11,318)
filter recall (E+S)        4.3%  (8,811/205,474)        5.1%  (10,551/205,474)
filter recall (Exact)      5.0%  (7,770/153,945)        6.0%  (9,176/153,945)
```

**Interpretation — hypothesis rejected.** OR-within-attribute moves Exact
recall from 5.0% to 6.0% (a 1-point absolute, ~20% relative improvement)
while *slightly reducing* precision (94.5% -> 93.2%, since OR
necessarily admits more candidate products, some of them wrong). This is
nowhere near the "few-fold" threshold set before running the experiment.
**The self-contradictory-conjunction mechanism identified in R1-E02 is
real (it does explain some lost recall — the ~1-point gain is genuine)
but is not the dominant cause.** The dominant cause is upstream of
aggregation logic entirely: most of the 206,227 brand values and 169,085
color values a naive cold-start profiler indexed from this real catalog
are not the *actual* brand/color of the products that are genuinely
relevant to a given query — extraction quality, not conjunction logic,
is the bottleneck. Loosening how extracted values combine cannot recover
recall that was never encoded in the extraction to begin with. This
sharpens R1-E02's prescription: a **candidate canonicalization/
validation step before indexing** (rejecting catalog field values that
don't look like genuine categorical attribute values — e.g. "Without
Lids", "10 Gallon", "Pencils" — before they ever become lexicon entries)
is the fix this evidence actually points to, not a compiler-side
aggregation change. Area 9's cold-start pipeline sketch (`raw catalog ->
deterministic profiling -> semantic problem compression -> model/
heuristic reasoning over compressed problems -> candidate
canonicalization -> deterministic bulk application`) names exactly this
missing step; Gate 6's implementation skipped straight from profiling to
bulk lexicon construction with no canonicalization stage at all, and this
result is the direct, measured cost of that gap.

**Caveats**: single run (deterministic, no variance to characterize).
Only tests one specific alternative aggregation rule; does not test
canonicalization itself (a heuristic validator for "does this string look
like a real color" was not built this round — flagged as the next
concrete follow-up rather than spending further time on aggregation-rule
variants that this result suggests are the wrong lever).

**Regression check**: none (experiment-only code in `round1-eval`, not
`commerce_core`; no production behavior changed).

**Next question**: this closes the aggregation-rule line of inquiry
cleanly (rejected) and points at value-canonicalization as the
higher-value fix — noted for R1-E06 (control plane / cold start on real
vocabulary) rather than pursued immediately, since R1-E03 (adversarial
query stress test) and R1-E04 (external baseline) are still open and
don't depend on resolving this.
